# 0.5.0: supervised live QA, and the migration runbook for this machine

Two parts:

- **A. Live QA** of the branch in real Herdr. Use a **scratch workspace** and a **scratch store**
  (`JOB_BOARD_HOME`), before anything is merged or installed. Nothing here touches the live
  boards, the real store or Herdr's real `config.toml`.
- **B. The real migration** on this machine (the LXC), after the PR is merged and 0.5.0 is
  installed.

The tests (`node --test`, 163 of them) fake Herdr. Part A checks what only real Herdr can show.
Run every step yourself and watch it; stop at the first surprise.

## A. Live QA (scratch workspace, scratch store)

### A0. Set up

In a plain shell (any pane):

```sh
export QA=/tmp/board-qa                      # outside your home: the write gate lets a checkout write here
mkdir -p "$QA" && cd "$QA"
git clone -q https://github.com/larrychannon/herdr-job-board.git checkout
git -C checkout checkout -q feat/one-board
export BOARD="$QA/checkout/board.mjs"
export JOB_BOARD_HOME="$QA/store"            # a board of its own: no migration, never the real store
node "$BOARD" version                        # 0.5.0
node "$BOARD" path                           # /tmp/board-qa/store/board.json
mkdir -p "$QA/one" "$QA/two" && git -C "$QA/one" init -q && git -C "$QA/two" init -q
```

Create two scratch workspaces (`qa-one` with its cwd in `$QA/one`, `qa-two` in `$QA/two`). In
each, start a Claude Code session (`claude`) in the first pane: these are the two coordinators,
A (in qa-one) and B (in qa-two). In each pane, `export QA BOARD JOB_BOARD_HOME` as above before
starting `claude`, so the board commands they run use the scratch store. Check that both show:

```sh
herdr agent list | jq -r '.result.agents[] | [.pane_id, .workspace_id, (.name // "-"), .cwd] | @tsv'
```

Write down A's pane (`$PA`, e.g. `wX:p1`) and B's (`$PB`). In a shell pane of each workspace,
also export `JOB_BOARD_HOME`. Run the QA commands with no `*_AGENT_ROLE` variable set (from a
job's worker session they would count as a worker's: no owner, no answers).

A board pane that `open` starts gets the store's path as `--board`, so it shows the scratch
store. Its own shell starts with Herdr's environment, though, without `JOB_BOARD_HOME`. That is
why A8 starts its pane by hand, in a shell with the scratch paths exported.

### A1. Cards of two projects, owners, tags

From a shell pane **in qa-two** (cwd `$QA/two`), with `HERDR_PANE_ID` set to B's pane so B owns
the card:

```sh
HERDR_PANE_ID=$PB node "$BOARD" add waiting "QA two: pick one" --desc "Routing test" --ask "Pick" --option "Go" --option "Later" --suggest "Go"
```

From a shell pane **in qa-one** (cwd `$QA/one`):

```sh
HERDR_PANE_ID=$PA node "$BOARD" add todo "QA one: a to-do"
node "$BOARD" projects                       # one (tag one), two (tag two); coordinators PA, PB live
node "$BOARD" json --project all | jq '.items[] | {id, project, origin, workspace}'
```

Expect: card 1 project `two`, origin `$PB`, workspace qa-two's id; card 2 project `one`, origin
`$PA`.

### A2. open, tags, strip, p / P, a strip click

In A's pane, ask A to run `node "$BOARD" open` (or run it in a shell pane of qa-one: the board
opens beside the pane that runs `open`, and that pane becomes its fallback). Check in the pane:

- the title `Job board · all projects · 1 needs you`; the strip `Projects: ▸all  two 1  one`;
  tags `two` and `one` in two colours;
- `p` shows `two` only (`(+0 …)` counts, `TO DO (0 · +1 other)`), `p` again shows `one`, `P` all;
- with the mouse on, click `one` in the strip, then `all`;
- card 1 open: its first line `two · Routing test`, and under its buttons
  `answers go to: two coordinator (<PB>)`.

### A3. A button to an owner in another workspace

In the pane in qa-one, press **Go** on card 1. Expect:

- B's chat (qa-two) receives exactly `Board card 1 (two · QA two: pick one): Go`, and A's
  doesn't;
- the card shows `sent: Go · HH:MM · to two coordinator (<PB>)`.

### A4. The owner gone: the second press

In qa-two, `/exit` B's Claude session (its pane stays). In qa-one:

```sh
HERDR_PANE_ID=$PB node "$BOARD" add waiting "QA two: second" --option "Yes"   # owner PB, now not running
```

In the board pane, press **Yes** on card 3. Expect the note
`no two coordinator is running: press Yes again to send it to the board's coordinator (one, pane <PA>)`
and nothing sent. Press **Yes** again within 10 s: A's chat receives
`Board card 3 (two · QA two: second): Yes`, and the card says `to one coordinator (<PA>)`.

### A5. answer (the Telegram path)

Start B's Claude session again in its pane (same pane id). From a shell pane in qa-one:

```sh
node "$BOARD" front show                     # <PA> (the pane that last opened the board)
HERDR_PANE_ID=$PA node "$BOARD" add waiting "QA two: telegram" --project two --option "Go" --option "Not now"
HERDR_PANE_ID=$PA node "$BOARD" answer 4 "not NOW" --from telegram
```

Card 4 is owned by A, so this answer goes to A: expect `card 4 is this pane's … act on it here:
Not now` (nothing sent). Then answer B's card 1:

```sh
HERDR_PANE_ID=$PA node "$BOARD" answer 1 2 --from telegram
```

Expect `sent to two coordinator (<PB>): Later`, and B's chat receives
`Board card 1 (two · QA two: pick one): Later (from Telegram)`. With B stopped,
`answer 1 Go` exits 1 with `… add --front`; `answer 1 Go --front` then goes to A.

### A6. report-metadata for another workspace (the sidebar)

The sidebar shows `$board` only with the row added (A7 does it on a copy; for this step add
`["$board"]` by hand to a **copy** of the config and start nothing from it: read the token
instead):

```sh
HERDR_PANE_ID=$PA HERDR_WORKSPACE_ID=<qa-one id> node "$BOARD" token   # this workspace's text; reports every workspace's
herdr workspace list | jq -r '.result.workspaces[] | [.workspace_id, .label, (.tokens.board // "-")] | @tsv'
```

Expect qa-two's token (`2 need you` or what its cards make) set by a command run in qa-one, and
qa-one's its own. This is the check the tests can't make: Herdr 0.9.x accepts a
`report-metadata` for another workspace.

### A7. setup --dry-run on a copy of config.toml

```sh
cp ~/.config/herdr/config.toml "$QA/config.toml"
HERDR_CONFIG_PATH="$QA/config.toml" node "$BOARD" setup --dry-run --key prefix+b          # stops: prefix+b is Herdr's toggle_sidebar
HERDR_CONFIG_PATH="$QA/config.toml" node "$BOARD" setup --dry-run                         # the default, prefix+shift+b
HERDR_CONFIG_PATH="$QA/config.toml" node "$BOARD" setup --no-reload
diff ~/.config/herdr/config.toml "$QA/config.toml"
HERDR_CONFIG_PATH="$QA/config.toml" herdr config check
HERDR_CONFIG_PATH="$QA/config.toml" node "$BOARD" setup --no-reload                       # "nothing to change"
```

Expect: the diff adds only the `[[keys.command]]` block and the `$board` row; `config check` is
clean; the second run changes nothing; `$QA/config.toml.bak-*` holds the copy as it was. Never
run it without `HERDR_CONFIG_PATH` here.

### A8. Self-update from 0.4.0

A 0.4.0 board pane updating itself to 0.5.0 in place. The pane is started **by hand in a scratch
shell**, not by `open`, so it runs with the scratch environment. Its `restart.log` then goes to
`$QA/state`, and after the import it follows the cards to `$QA/store`. A pane that `open` starts
gets Herdr's environment instead, and would log to the real state folder.

In a new tab of qa-one (a shell pane; call it the A8 pane):

```sh
export QA=/tmp/board-qa BOARD=/tmp/board-qa/checkout/board.mjs
export JOB_BOARD_HOME="$QA/store" XDG_STATE_HOME="$QA/state"      # every path in scratch, for this pane and what it starts
git clone -q https://github.com/larrychannon/herdr-job-board.git "$QA/plugin"
git -C "$QA/plugin" checkout -q 6f4047a                  # 0.4.0
mkdir -p "$QA/eight" && cd "$QA/eight" && git init -q && git commit -q --allow-empty -m init
node "$QA/plugin/board.mjs" add waiting "0.4 card: approve" --option "Go"    # writes $QA/eight/.git/job-board.json (0.4)
node "$QA/plugin/board-pane.mjs" --board "$QA/eight/.git/job-board.json" --origin "$PA" --version 0.4.0
```

The board (0.4.0) now runs in the A8 pane. From another shell pane, update its copy in place, as
`herdr plugin install` does:

```sh
git -C /tmp/board-qa/plugin checkout -q feat/one-board
```

Expect, within about 10 s:

- the A8 pane says board 0.5.0 is installed, quits, and starts 0.5.0 in the same pane, in the same
  shell (with the exports above);
- it shows `0.4 card: approve`, read from the 0.4 file;
- `cat /tmp/board-qa/state/herdr-job-board/restart.log` has the restart, and
  `/root/.local/state/herdr-job-board/restart.log` is unchanged (check its time before and after).

`JOB_BOARD_HOME` is set, so nothing migrates by itself. Then, from the other shell pane:

```sh
cd /tmp/board-qa/eight && JOB_BOARD_HOME=/tmp/board-qa/store node /tmp/board-qa/checkout/board.mjs import /tmp/board-qa/eight/.git/job-board.json
```

The 0.4 file becomes `job-board.migrated.json` (the import prints the exact name). Within a
refresh, the A8 pane follows the cards into `$QA/store`: its title becomes
`Job board · all projects`, still showing `0.4 card: approve`.

### A9. herdr plugin link and unlink (for the rollback, B3)

B3 puts 0.4.0 back with `herdr plugin uninstall`, then `herdr plugin link`. Check that link and
unlink behave on a copy with **another plugin id**, so the installed plugin is never touched:

```sh
cp -r /tmp/board-qa/plugin /tmp/board-qa/plugin-qa
sed -i 's/^id = "herdr-job-board"/id = "herdr-job-board-qa"/' /tmp/board-qa/plugin-qa/herdr-plugin.toml
grep -n '^id' /tmp/board-qa/plugin-qa/herdr-plugin.toml               # id = "herdr-job-board-qa"
herdr plugin link /tmp/board-qa/plugin-qa
herdr plugin list --json | jq -r '.result.plugins[] | [.plugin_id, .version, .plugin_root] | @tsv'
herdr plugin unlink herdr-job-board-qa
```

Expect the qa id listed with root `/tmp/board-qa/plugin-qa`, then gone. If `herdr-plugin.toml`
names the id differently (no `id =` line), skip this step and note it: B3 then stays unverified on
this point.

### A10. Clean up

Quit the boards in the scratch panes (`q`), close the two scratch workspaces, and
`rm -rf /tmp/board-qa`. The real store, boards and config were never used. Part B clones its own
copy.

## B. The real migration on this machine (after merge and install)

The live boards today: `/root/sfc-integration/.git/job-board.json` (about 197 cards, ids up to
216) and `/root/ai-config/.git/job-board.json` (1 card, `fix-x`, a stale test card). The store
`/root/.local/state/herdr-job-board/` holds only `restart.log`.

### B0. Before installing: no leftovers, then the dry run

**First, no leftover migrated copies.** A `job-board.migrated*.json` beside a live board would
be a second "old file" next to the one the import makes; stop and move it away first:

```sh
ls -la /root/sfc-integration/.git/job-board.migrated*.json /root/ai-config/.git/job-board.migrated*.json 2>/dev/null \
  && echo "STOP: move these out of .git before installing" || echo "ok: no leftovers"
```

(The 19 Oct incident's copy beside sfc's board was already moved out by the coordinator.)

**Then the dry run.** It writes nothing. A scratch `JOB_BOARD_HOME` previews against an empty
store, which is what the real one is today:

```sh
git clone -q https://github.com/larrychannon/herdr-job-board.git /tmp/board-dryrun && git -C /tmp/board-dryrun checkout -q feat/one-board
cd /root/sfc-integration
JOB_BOARD_HOME=$(mktemp -d) node /tmp/board-dryrun/board.mjs import --dry-run
```

Check the preview:

- sfc-integration: all cards, `ids kept (1–…)`;
- ai-config: `fix-x … left out`;
- the suggested re-tags;
- `archive: N Done cards older than 7 days go to archive/`;
- `then: board.json … next_id …`.

Then `rm -rf /tmp/board-dryrun`.

### B1. Install, then import with the re-tags, from the sfc coordinator

Merge PR #2, then `herdr plugin install larrychannon/herdr-job-board`. The board panes update
themselves within seconds and keep showing the 0.4 file until it is brought in. **Straight
away**, from the sfc coordinator's pane (w4:p6), so the sfc cards become its own:

```sh
BOARD="$(herdr plugin list --json | jq -r '.result.plugins[] | select(.plugin_id == "herdr-job-board") | .plugin_root')/board.mjs"
node "$BOARD" version                                   # 0.5.0
cd /root/sfc-integration
node "$BOARD" import --retag 200=home,204=ai-config,206=ai-config,207=herdr-job-board,209=ai-config,211=herdr-job-board
```

Card 213 stays in sfc-integration. The import ends with one line per 0.4 file:
`<repo>/.git/job-board.json → <repo>/.git/job-board.migrated.json`. Keep that output: these
are the files a rollback puts back. The store records them too, in `imports[].renamed`. If a
write (a wait script, a button) brought the boards in first, the same command shows that import
and applies the re-tags (`import: nothing left to bring in; brought in automatically on …`, then
`re-tagged: …`). A card an automatic import left unowned becomes the coordinator's when it
re-tags or edits it.

### B2. Checks

```sh
node "$BOARD" projects                    # sfc-integration (sfc), ai-config (ai), herdr-job-board (herdr), home
node "$BOARD" json --project all | jq '.items | length, (map(.project) | group_by(.) | map({(.[0]): length}) | add)'
node "$BOARD" json --project all | jq -r '.imports[] | [.project, .cards, .renamed, .backup] | @tsv'
ls -la /root/sfc-integration/.git/ /root/ai-config/.git/ | grep job-board   # job-board.migrated.json only, no job-board.json
ls /root/.local/state/herdr-job-board/ /root/.local/state/herdr-job-board/backups/   # board.json, archive/, backups/import-…/
node "$BOARD" ls --width 95               # this project's cards, "+N open cards in other projects"
node "$BOARD" doctor
```

Expect:

- card counts that match the dry run;
- 200 is home's; 204, 206 and 209 are ai-config's; 207 and 211 are herdr-job-board's;
- `fix-x` is not on the board (it stays in the backup and the renamed file);
- the sfc board pane now shows `Job board · all projects` with tags;
- doctor: everything ok but the key and sidebar.

Then:

```sh
node "$BOARD" front                        # the sfc coordinator holds Telegram
node "$BOARD" setup --dry-run              # prefix+shift+b, and "$board" in the sidebar rows
node "$BOARD" setup                        # backup, config check, reload-config
```

Press `prefix+shift+b`: the board opens beside the focused pane. The sidebar shows each
workspace's counts.

### B3. Rollback (if something is wrong)

1. **The boards.** Choose one of these, per repo:
   - The cards as they are now (anything written since the import included), as a 0.4 board:

     ```sh
     node "$BOARD" export --legacy --project sfc-integration > /tmp/sfc-board.json
     node "$BOARD" export --legacy --project ai-config > /tmp/ai-board.json
     ```

     Put each back as `<repo>/.git/job-board.json` once 0.4.0 runs (step 2).
   - The board exactly as it was at the import: the file the import renamed, by the name it
     recorded (never another `job-board.migrated*.json` that may be lying there):

     ```sh
     node "$BOARD" json --project all | jq -r '.imports[] | select(.renamed) | "\(.renamed)\t\(.from)"' |
       while IFS=$'\t' read -r renamed from; do mv -n "$renamed" "$from" && echo "back: $from"; done
     ```

   Cards re-tagged to another project (200, 204, …) are exported with their new project; a
   re-tagged card of sfc's is in ai-config's export, for example. `export --legacy --project all`
   gives every card in one file.
2. **The plugin.** Herdr's `plugin install` takes no version, so remove 0.5.0 and link a checkout
   of 0.4.0 (A9 checked link and unlink):

   ```sh
   git clone -q https://github.com/larrychannon/herdr-job-board.git /root/herdr-job-board-0.4 && git -C /root/herdr-job-board-0.4 checkout -q 6f4047a
   herdr plugin uninstall herdr-job-board
   herdr plugin link /root/herdr-job-board-0.4
   herdr plugin list --json | jq -r '.result.plugins[] | select(.plugin_id == "herdr-job-board") | [.version, .plugin_root] | @tsv'   # 0.4.0  /root/herdr-job-board-0.4
   ```

3. **The board panes.** 0.4.0's `restart` doesn't move a 0.5 pane: its copy isn't 0.4.0's. In
   each tab that has a board pane, from the pane you work in (the coordinator's):

   ```sh
   node /root/herdr-job-board-0.4/board.mjs open
   ```

   It quits the board running there (another copy) and starts 0.4.0 on that repo's
   `.git/job-board.json`: `board switched to this copy in pane …`. If it says something else
   runs in the pane, press `q` in the board pane and run `open` again.

4. The store `/root/.local/state/herdr-job-board/` stays where it is, for another try. A
   `.git/job-board.json` that 0.4 writes meanwhile is what the next 0.5 import merges.
